## 1. 專案目標

建立一個常駐在個人 Windows 電腦上的 Telegram 機器人，讓不熟悉電腦操作的家人，只要在對話視窗點按鈕、傳照片，就能把照片存到指定的資料夾。核心原則是「**簡單、防呆、零刪除**」。

## 2. 核心設計原則

| 原則 | 說明 |
|---|---|
| **目的地零刪除、零移動** | 對「區網硬碟」與「OneDrive」，程式只會「複製」與「建立資料夾」，完全不具備刪除或移動能力。<br>**唯一例外**：暫存區（見下列）。 |
| **暫存區可刪（受圍籬限制）** | 暫存區是程式自己的工作空間，該批複製成功後即刪除以釋放空間。`storage.py` 的刪除函式會先驗證路徑是否位於暫存區底下，**不是就拒絕執行**，確保刪除能力永遠碰不到目的地。 |
| **照片不遺失** | 照片一律先落地暫存區，確認複製到目的地成功後才清除暫存；失敗則保留並重試。 |
| **確定性邏輯，不用 LLM** | 全部用規則（if/else）處理，不引入 LLM，避免幻覺、降低成本、易於除錯。 |
| **對家人友善** | 一切從按鈕開始，錯誤訊息簡單，不揭露背後運作細節。 |
| **管理員全知** | 所有事件（成功、傳錯、失敗、新成員、非授權來訊）都通知固定的管理員帳號。 |
| **通知失敗不可中斷本體工作** | 發送 Telegram 狀態／進度訊息本身也可能因網路瞬斷而失敗（如 `NetworkError`）。此類失敗**只能記錄，絕不允許中止正在進行的照片複製流程**——曾發生進度訊息發送失敗導致整批複製中途卡死、後續照片滯留暫存區的情形，故所有狀態通知一律包成「失敗即記錄、不拋例外」，與實際檔案寫入邏輯完全脫鉤。 |
| **事件處理不可被慢工作阻塞** | Telegram 的 update（家人傳的照片、按下的按鈕）預設是**一則處理完才處理下一則**。若把「下載照片」「複製到網芳」這類耗時工作直接寫在事件處理函式裡，後面排隊的按鈕點擊就會被卡住——使用者按了「✅ 我傳完了」卻毫無反應，甚至因 Telegram 的 callback 逾時（約 15 秒）而**整個點擊被丟棄**。故事件處理函式一律只做「登記 ＋ 回覆」等毫秒級動作，所有耗時工作交由背景 worker 執行（見 §3.1）。 |
| **記錄檔寫入失敗不可中斷本體工作** | 與上一條「通知失敗不可中斷本體工作」同一原則，適用對象擴及 `upload_log.csv`／`file_index.csv`／`待清理清單.csv`／`members.json`。<br>實測踩過的坑：管理員用 Excel 開著 `待清理清單.csv`（那正是這個檔案存在的目的——照著它刪檔），Windows 鎖檔使寫入拋 `PermissionError`，例外一路往上炸掉整個「這批傳錯了」流程——照片**其實已經複製完成**，卻沒回覆使用者、沒寫 `file_index`、新資料夾沒進「最近使用」，且 `corrected` 旗標已設導致連重試都不行。<br>故所有記錄檔寫入一律「**失敗即記 log ＋ 通知管理員 ＋ 繼續執行**」，並把未寫入的內容留在 `logs/photo-bot.log` 供人工補回。<br>**副則**：使用者看得到的結果（回覆訊息、「最近使用的資料夾」）必須排在記錄檔寫入**之前**，才不會被記錄層的問題連累。 |
| **絕不對目的地做破壞性寫入** | 「零刪除」不只是「不呼叫 delete」。**覆蓋既有檔案同樣是破壞性操作**——`shutil.copy2` 底層是 `open(dst, 'wb')`，開檔當下原檔就歸零，複製途中若網芳斷線（本專案實際遇過 WinError 50，見 §4.1），結果是「原本那張照片沒了、新的那張又不完整」，兩張都救不回來。故目的地一律只新增檔案，撞名必須另存（見 §10）。**漏存可以補救，覆蓋掉的照片救不回來。** |
| **並行必須有明確上限** | 背景化不等於放任。下載與複製一律由**固定數量**的背景 worker 從佇列取件執行，並行度**不隨照片數量增加**——一次傳幾千張與一次傳十張，對磁碟與網芳的瞬時壓力完全相同（見 §6.3.3）。 |
| **可擴充** | 模組化架構，未來新增功能不影響既有邏輯。 |

## 3. 系統架構

```
家人手機 (Telegram)
      │  傳照片 + 選/打資料夾名稱
      ▼
  Python Bot（你的 Windows 電腦，手動啟動）
      │
      ├─【事件處理層：毫秒級、序列】────────────────────────
      │     收到照片 update → 登記 file_id、張數 +1 → 更新畫面 → 立即返回
      │     收到按鈕點擊    → 立即回覆
      │              │  只把工作丟進佇列，絕不等它做完
      │              ▼
      ├─【背景 worker 層：固定數量，見 §6.3.3】──────────────
      │     ├─① 下載 worker ×N → 照片落地到「暫存區」（安全著陸）
      │     │        │
      │     │        ▼
      │     └─② 複製 worker ×1 → 每滿一批（預設 20 張）複製到目的地
      │              ├──▶ 區網硬碟   \\192.168.1.1\g\照片
      │              └──▶ OneDrive   本機同步夾（自動上雲）
      │              │
      │              └─③ 該批確認成功 → 刪除暫存區該批檔案（釋放空間）
      │                    失敗 → 保留暫存 + 重試 → 仍失敗則通知管理員
      │
      ├─④ session 結束 → 對 OneDrive 該批執行「釋放空間」
      └─⑤ 通知管理員（Telegram 私訊）＋ 寫入上傳紀錄 CSV
```

**暫存中繼的用意**：Telegram 的照片本就需先下載到本機，明確落地到指定暫存區可確保「照片一定不會遺失」；複製失敗時重試即從暫存區再送一次；每批成功即清除，暫存區永遠只留「尚未成功」的檔案，不會膨脹。

### 3.1 事件處理與背景工作的分離（v3 架構準則，最重要）

**問題的由來**

python-telegram-bot 預設 `max_concurrent_updates=1`：**一則 update 沒處理完，就不會去取下一則**。家人傳的每一張照片是一則 update，按下的每一顆按鈕也是一則 update，全部共用同一條佇列。

v2 把「下載照片」與「每滿 20 張複製到目的地」直接寫在照片處理函式裡同步等待完成。以「🏠☁️ 兩邊都存」為例，光是每批 20 張的寫入節流就是 `20 × 0.3 秒 × 2 個目的地 = 12 秒`，再加上實際的下載與 SMB 複製時間——這段期間佇列完全停滯，使用者按下的「✅ 我傳完了」只能在後面排隊。實測上百張時，佇列可積壓一至兩分鐘，症狀就是：

- 收件計數的張數「都傳完之後才跳出來」；
- 按「✅ 我傳完了」**完全沒有反應**；
- 更糟的是，Telegram 的 callback query 約 **15 秒**後失效，積壓超過這個時間，該次點擊會直接報錯被丟棄，使用者的「我傳完了」等於從未按下，session 一路卡到 10 分鐘逾時才由保險機制收尾。

> ⚠️ **`asyncio.to_thread()` 解決不了這件事**。§3 技術選型的 I/O 隔離準則只保證「檔案寫入不會凍結事件迴圈」，但處理函式本身仍在 `await`、仍未返回，佇列照樣被堵住。**「不凍結事件迴圈」與「不堵住 update 佇列」是兩件不同的事**，v2 只做到前者。

**v3 的分工**

| 層 | 職責 | 時間尺度 | 並行度 |
|---|---|---|---|
| **事件處理層** | 只做「登記 ＋ 回覆」：記下 `file_id`、張數 +1、更新畫面訊息、重設緩衝計時、回應按鈕 | **毫秒級** | 1（維持序列） |
| **下載 worker** | 從佇列取件，向 Telegram 下載照片、落地暫存區 | 秒級 | 固定 `DOWNLOAD_WORKERS`（預設 3） |
| **複製 worker** | 累積滿一個內部小批即複製到各目的地、成功後刪暫存 | 十秒～分鐘級 | 固定 1（網芳最怕並行寫） |

**為何不改用 `concurrent_updates=True`**

讓多則 update 並行處理雖然也能解除阻塞，但會讓 session 狀態（張數、暫存夾、目的地寫入結果）暴露在資料競爭下，需要另外加鎖，風險遠高於收益。**只要事件處理層本身是毫秒級的，序列處理就不再是瓶頸**——維持序列反而白白換到「session 狀態天生不會被並行改壞」的保證。這是 v3 刻意的選擇。

**衍生的正面效果**

- 「已收到 X 張」在**收到當下**就準確，不必等下載完成才計數（v2 的張數天生落後於實際收到量）。
- 使用者主動操作（按鈕）永遠即時回應，不受背景工作量影響。

### 技術選型

| 項目 | 決定 | 理由 |
|---|---|---|
| 平台 | **Telegram** | Bot API 免費無上限；可保留原圖畫質；建置容易。 |
| 後端 | **個人 Windows 電腦**，開機自啟 | 需同時碰到區網硬碟與網際網路，故必須在家中。 |
| 語言 | **Python（純寫檔）** | 用 `shutil.copy2` + `Path.mkdir`，不經 PowerShell，減少出錯面。 |
| 檔案操作 | 只用「複製」與「建夾」 | 程式不含任何刪除／移動指令。 |
| 是否用 LLM | **否** | 需求為規則明確的檔案搬運，用確定性邏輯更可靠。 |
| **I/O 隔離（架構準則）** | **所有檔案 I/O 一律以 `asyncio.to_thread()` 執行** | Telegram 框架採 asyncio 事件迴圈，而 `shutil.copy2` 對 SMB 網芳的寫入是**同步阻塞**呼叫。若不隔離，寫入期間會凍結整個事件迴圈——其他家人傳訊完全無回應，進度條與「輸入中」狀態也無法更新。此為 `storage.py` 的強制準則。 |
| **事件佇列不阻塞（架構準則）** | **事件處理函式一律毫秒級返回；耗時工作交背景 worker** | `asyncio.to_thread()` 只解決「不凍結事件迴圈」，**不解決「update 佇列被前一則堵住」**——這是兩件不同的事。詳見 §3.1。 |
| 併發寫入控制 | 單一寫入佇列 ＋ 原子寫入 | `members.json`／`upload_log.csv` 由單一背景執行緒依序寫入（見 §10C）。 |

## 4. 儲存位置說明

### 4.1 區網硬碟
- **實際路徑**：`\\192.168.1.1\g\照片`（UNC，TP-Link 路由器 USB 網芳）。
- **連線帳號**：`hn14332019`（讀寫），憑證已由 Windows 記住，故 bot 免帳密即可寫入（詳見 §11A）。
- 已實測：連得到、可建中文資料夾、可寫檔，全數通過。
- 現有內容：硬碟中已有約 191 個以「時間+事件」命名的相簿資料夾（如「110嘉義家族旅遊」），與本專案的資料夾命名機制相容。

**連線健檢機制**

即使後端電腦保持開機，SMB 連線仍可能中斷，原因包括：路由器重啟（韌體更新、跳電、手動重開）、Windows 強制更新重開、路由器主動斷開閒置連線、網路介面卡進入省電模式等。

| 時機 | 動作 |
|---|---|
| 程式啟動時 | 執行一次寫入健檢 |
| 每次開啟上傳 session 時 | 執行一次寫入健檢 |

**健檢做法**：於目的地寫入一個極小的暫存測試檔，確認成功後刪除（此刪除屬程式自身產生的健檢檔，不涉及任何照片）。異常則**立即通知管理員**，並提示使用者稍後再試——寧可事前攔阻，也不要收下照片後才發現無法寫入。

**區網硬碟可關閉（`ENABLE_NAS`）**

實測時曾遇到路由器端 USB 分享暫時性故障（SMB 寫入回傳 WinError 50，經確認為路由器/檔案系統層暫時唯讀，非程式或權限問題，重開機後恢復）。為避免硬碟異常期間整個上傳功能都不可用，新增 `config.py` 開關 `ENABLE_NAS`：

- 設為 `False` 時：目的地選擇鍵盤**隱藏**「🏠 家裡硬碟」與「🏠☁️ 兩邊都存」兩個選項，僅保留「☁️ OneDrive」；啟動健檢與 session 健檢**跳過**區網硬碟這一項。
- 設為 `True`（預設）：行為與原規格相同，三個目的地選項全部顯示。
- 此開關**不影響零刪除保證**，僅是「這個目的地暫時不參與分流」的開關，硬碟本身內容完全不受影響。

### 4.2 OneDrive
- 直接寫入本機的 OneDrive 同步資料夾（路徑於 `config.py` 設定）。
- 寫入後由 OneDrive 用戶端**自動上傳**，程式不需呼叫 Microsoft Graph API。

**「成功」的判準（重要）**
- 本專案定義的「上傳成功」＝**檔案已寫入本機 OneDrive 同步資料夾**。
- ⚠️ 這**不等同於雲端已收到**。程式無法直接查詢 OneDrive 的雲端同步狀態，實際上傳由 OneDrive 用戶端在背景進行。
- 因此所有通知文字須明確表達此語意，例如：
  `✅ 完成！100 張 → 阿嬤生日（OneDrive）`
  `☁️ 雲端同步需要一點時間，稍後再到 OneDrive 查看`

**釋放本機空間**
- **時機**：該批照片寫入完成後，**延遲 `ONEDRIVE_FREE_SPACE_DELAY_MIN` 分鐘（預設 10）才執行**，以 job queue 排程。
- **做法**：對該批寫入 OneDrive 的檔案執行 Windows 指令 `attrib +U -P`，標記為「僅線上」。
- ⚠️ **絕不可在批次結束當下立刻執行（v3.6 實測修正）**：那時 OneDrive 用戶端通常**還沒把檔案傳到雲端**，雲端沒有副本可以「僅線上」，`attrib +U` 沒有東西可以指向、**不會生效**。<br>實測證據：使用者上傳 24 張照片後，這些檔案的屬性**全部只有 `A`、完全沒有 `U`**——標記從頭到尾沒生效過；而對同一個檔案在閒置一段時間後手動下同一道指令，立刻就生效（顯示 `U`）。證明指令本身沒問題，純粹是時機太早。
- **這個 bug 的表面症狀**：使用者會看到「服務跑完後，OneDrive 突然開始動作，然後照片變成本機檔（綠色勾勾）」，誤以為是程式或 OneDrive 在「自動下載」。實際上那只是 OneDrive 在完成它自己的正常上傳流程，而我們的標記從未生效。
- **原規格的錯誤假設**：v3.5 以前寫「若檔案尚未同步完成，OneDrive 會等同步完成後才真正轉為僅線上」——**此假設經實測不成立**，未同步完成的檔案下 `attrib +U` 是無效的，不是延後生效。
- **與零刪除原則的關係**：此動作移除的是**本機快取副本**，照片本體仍在雲端，且區網硬碟另有一份，故不違背保護照片本體的原則。
- 可於 `config.py` 以開關關閉此功能。

### 4.3 暫存區（中繼站）
- **預設位置**：`D:\photo-bot-temp`（於 `config.py` 設定，可隨時更改；建議放空間充足的磁碟）。
- **角色**：所有從 Telegram 下載的照片**先落地於此**，再分批複製到目的地。不只是失敗緩衝，而是整條流程的中繼站。

**三層分區結構（避免多人／多批混淆）**

```
D:\photo-bot-temp\
├── 123456789_秀琴\                 ← 第一層：使用者（Telegram ID_名字）
│   ├── 20260723_2140_阿嬤生日\      ← 第二層：本次上傳（時間戳_目標資料夾）
│   │   ├── 20260723_214005_123456.jpg
│   │   └── ...
│   └── 20260723_2230_過年聚餐\
└── 987654321_大姊\
    └── 20260723_2145_烤肉\
```

| 層級 | 命名 | 用途 |
|---|---|---|
| 第一層 | `{TelegramID}_{名字}` | 區隔不同使用者，多人同時作業互不干擾 |
| 第二層 | `{時間戳}_{目標資料夾名}` | 區隔同一人的**每一次上傳**。同一人可能先後兩次傳到同一資料夾（例：先傳 100 張到「阿嬤生日」，完成後再傳 20 張），加時間戳才能明確切分，「這批傳錯了」也才能精準對應 |

**此結構帶來的效益**
- 多人同時上傳不會互相污染，計數精準。
- 「這批傳錯了」直接對應單一暫存子夾，範圍明確。
- 程式中斷重啟後，可從暫存夾結構判讀誰的哪一批尚未完成。

**清理機制**
- 每個內部小批複製到所有目的地成功後，**立即刪除該批的暫存檔**。
- 該次上傳全部完成後，刪除該次的第二層暫存子夾（空夾）。
- **失敗保留**：複製失敗的檔案保留於暫存區供重試；重試仍失敗則通知管理員，檔案續留不刪。
- **刪除圍籬**：程式的刪除功能僅允許作用於 `TEMP_DIR` 底下，`storage.py` 會在執行前驗證路徑，非暫存區一律拒絕執行。

**「兩邊都存」的部分失敗語意**

當目的地選擇「🏠☁️ 兩邊都存」，而其中一邊成功、另一邊失敗時：

| 項目 | 處理方式 |
|---|---|
| 整體判定 | **任一目的地失敗，即視為該批未完成** |
| 暫存檔 | **不刪除**，保留供重試 |
| 重試範圍 | **僅重試失敗的那一個目的地**，已成功的不重複寫入（避免產生重複檔案） |
| 使用者通知 | 「有一部分還在處理中，已通知管理員」 |
| 管理員通知 | 分別列出兩邊狀態，例如：`家裡硬碟 ✅ 100 張／OneDrive ❌ 失敗（原因）` |

**程式非預期中斷後的復原策略**

程式若因斷電、當機、手動中止而中斷，重啟後執行以下流程：

1. **啟動時掃描 `TEMP_DIR`**，尋找所有未完成的暫存子夾。
2. 讀取該子夾內的 **`_session_info.json` 側車檔**（見下方說明），取得該批**正確的目的地與資料夾名**。
3. **嘗試自動補送**至原目標資料夾（含「兩邊都存」時的兩個目的地）。
4. 補送成功 → 清除該批暫存；補送失敗 → **保留暫存不刪**，通知管理員人工處理。
5. 補送的每一張照片，比照正常流程**寫入 `file_index.csv`**（含 file_id），並在 `upload_log.csv` 記一筆結果為「成功(復原)」／「部分失敗(復原)」的紀錄——**復原批次與正常批次享有相同的可追溯性**，不因中斷而漏記索引。
6. 一律通知管理員復原結果（哪些批次、幾張、成功或失敗）。

> 復原過程**永不刪除未確認成功的檔案**，寧可留下待處理的暫存，也不冒遺失風險。

**`_session_info.json` 側車檔（判定正確目的地的依據）**

記憶體中的 session 狀態（使用者選了哪個目的地、哪個資料夾）在程式崩潰時會遺失。若只靠暫存子夾名稱（`{時間戳}_{目標資料夾}`）反推，只能得知資料夾名，**得不到目的地**（家裡硬碟／OneDrive／兩邊都存）。因此使用者一選定目的地與資料夾，程式即在該次暫存子夾內同步寫入一份極小的 `_session_info.json`（內容：目的地、資料夾名、Telegram ID、姓名），供中斷後精準復原之用，不需臆測。若因更早期的暫存資料缺少此側車檔（例如程式更新前留下的殘留），復原時退回保守猜測並在管理員通知中明確標示「無法確認原目的地，已用預設猜測，請人工核對」。

## 5. 成員管理與註冊機制

### 5.1 註冊流程

**進入點：使用者不需先傳送任何訊息**

Telegram 的機制是：使用者首次開啟 bot 對話時，畫面會顯示一顆 **START** 按鈕，點下後 bot 即收到 `/start` 訊號並可**主動發出第一則訊息**。因此家人一進來就直接看到按鈕，**不需要自己想該打什麼字**。

```
（使用者點畫面上的 START）
Bot:   👋 歡迎！第一次使用要先登記一下
       請點下方按鈕開始
       [📝 我要註冊]
```

**完整流程**

1. 使用者首次開啟對話 → 點 START → **bot 主動發送歡迎訊息與 `📝 我要註冊` 按鈕**。
2. 使用者點 `📝 我要註冊` → bot 才詢問稱呼：

```
Bot:   請告訴我怎麼稱呼你？（例如：媽媽、大姊）
       直接打字告訴我就好
```

3. 使用者輸入稱呼 → 寫入成員清單 `members.json`，狀態為「**待審核**」。
4. bot 通知管理員：新成員的**名字 + Telegram ID**，並附上 `[✅ 開通]` `[❌ 拒絕]` 按鈕。
5. **管理員按「✅ 開通」後**，該成員狀態改為「已開通」，才能使用；bot 主動通知使用者「已開通，可以開始用了」並附上原圖畫質教學（見 §5.3）。

**各種狀態下的來訊處理**

| 使用者狀態 | bot 回應 |
|---|---|
| 從未登記（含首次 START、或之後任何來訊） | 顯示歡迎訊息 ＋ `📝 我要註冊` 按鈕 |
| 已登記、待審核 | 「已收到登記，等管理員開通後就能使用」＋通知管理員 |
| 已拒絕 | 仍顯示 `📝 我要註冊` 按鈕可重新登記，再次通知管理員審核 |
| 已開通 | 正常進入上傳流程（顯示 `📷 我要上傳照片`） |

> **設計原則**：任何狀態下，使用者畫面上**永遠有可點的按鈕**，不會出現「不知道要做什麼」的空白狀態。
> **安全性說明**：引導註冊不降低安全性，真正的關卡始終是「管理員按開通」，未開通者無法使用任何上傳功能。

### 5.3 註冊完成時的原圖畫質教學

Telegram 手機版**預設以壓縮方式傳送照片**（長邊約 1280px），會損失原始畫質。為兼顧畫質與易用性，採三層策略：

| 層級 | 做法 |
|---|---|
| **程式兩種都收** | 同時接收 `photo`（壓縮版）與 `document`（原檔），確保無論如何都收得到照片，不會漏失 |
| **註冊完成時教學** | 開通後發送圖文說明，教導如何以原始畫質傳送：傳送時選「以檔案傳送」，或於 Telegram 設定中關閉照片壓縮 |
| **偵測後溫和提醒** | 若偵測到本次傳送的是壓縮版，於該 session **僅提醒一次**（不重複打擾），提示可改用原檔方式傳送 |

### 5.2 成員清單（members.json）
- **存放位置**：後端電腦本機的專案資料夾內（如 `C:\photo-bot\data\members.json`）。**不外傳、不上雲**，只有這台電腦看得到。
- **可讀性**：純文字檔，可用記事本直接打開，或請 bot 回報清單。
- 記錄欄位：

| 欄位 | 範例 |
|---|---|
| 名字 | 秀琴 |
| Telegram ID | 123456789 |
| 加入時間 | 2026-07-22 10:30 |
| 狀態 | 待審核 / 已開通 / 已拒絕 |

- 管理員可隨時查詢完整清單。

## 6. 上傳流程

### 6.1 啟動
- 對話視窗輸入框下方**常駐一顆按鈕**：`📷 我要上傳照片`。
- 家人點此按鈕，才會啟動一次「上傳工作階段」。
- 若在**未啟動**狀態直接打字 → bot 回覆「請點下方的『📷 我要上傳照片』開始喔」。

### 6.2 選擇資料夾與目的地
- 啟動後，bot 顯示「目前資料夾 + 目的地」。
- 選擇資料夾的方式（兩種皆可）：
  - 點選「近 3 次用過的資料夾」按鈕；或
  - 直接打字輸入新資料夾名稱。

**資料夾已存在時要明確告知（v3.3 新增）**

使用者選定目的地後，若該資料夾在目的地**已經存在**，`✅ 準備好了！` 訊息須加一句：

```
📁 「去年中秋」這個資料夾已經有了（家裡硬碟），照片會直接存進去，不會另外開新的
```

讓使用者分得清這次是「開一本新相簿」還是「加進既有相簿」——不講的話他無從分辨，可能以為打錯字開了重複的相簿，或反過來以為開了新的、結果混進舊照片裡。「📦 兩邊都存」時列出實際存在的那幾個目的地。

存在性檢查可能打到網芳，須以 `asyncio.to_thread()` 執行（§3）；檢查本身失敗只是少一句提示，不影響上傳。

**「近 3 次資料夾」的定義**
- **各使用者獨立記憶**，不共用（秀琴看到的是秀琴的近期紀錄）。
- **不綁定目的地**：僅記錄資料夾名稱，選擇後**仍會另行詢問目的地**。
- 按鈕前綴以圖示標示該資料夾**上次存放的位置**，供使用者參考：
  `🏠 阿嬤生日`（上次存家裡硬碟）／`☁️ 過年聚餐`（上次存 OneDrive）／`🏠☁️ 除夕`（上次兩邊都存）
- 若是**新資料夾**，接著詢問目的地，共 **3 個選項**：
  `🏠 家裡硬碟` ／ `☁️ OneDrive` ／ `🏠☁️ 兩邊都存`

### 6.3 傳照片與分批上傳

**批次的定義（重要）**

「**一次上傳**」＝ 家人從開始傳照片，到**按下「✅ 我傳完了」按鈕**為止的全部照片。採明確按鈕判定，**不使用靜置時間推測**，以避免「她還在傳、系統卻誤判結束」。

**「登記」與「落地」是兩件事（v3 新增，重要）**

| 動作 | 何時發生 | 用途 |
|---|---|---|
| **登記** | 收到 update 的**當下**（毫秒級，純記憶體） | 記下 `file_id`、張數 +1。**所有對使用者顯示的張數、以及緩衝計時的重設，一律以「已登記」為準** |
| **落地** | 背景下載 worker 完成下載、寫入暫存區之後 | 照片實體存在於本機，才有後續複製到目的地的可能 |

如此一來「已收到 X 張」在收到當下就是準確的，不會因為下載還沒跑完而落後於實際狀況（v2 的計數是在下載完成後才 +1，故天生落後）。相對地，**緩衝結束、正式開始收尾時，必須先等待所有尚未完成的下載工作全部落地**，才能開始統計與複製（見下方流程第 5 步）。

**結案緩衝（Debounce，5 秒）**

按下「✅ 我傳完了」後**不立即結案**，先進入 5 秒緩衝：

- 手機端傳送照片是非同步的，按下按鈕當下可能仍有照片在背景傳輸中（長輩網路較慢時尤其常見）。
- 緩衝期間若收到新照片 → **重新計時 5 秒**，並將該照片計入本批。
- 連續 5 秒無新照片 → 正式結案。
- 緩衝期間 UI 顯示 `⏳ 確認中…`，避免使用者誤以為卡住。

> 結束的**判定權仍在按鈕**，5 秒僅為防止漏收的安全緩衝，非時間推測。

**緩衝期間的畫面更新採節流，但計時永遠準確（重要）**

點下「✅ 我傳完了」後，若緩衝期間持續有新照片湧入（例如使用者一次選了很多張、按送出，這些照片還在陸續抵達 bot），需拆成三件事分開處理：

- **按鈕回應（永遠即時）**：點下「✅ 我傳完了」的當下就必須看到「⏳ 確認中…」。此回覆由事件處理層直接送出，不排在任何下載或複製工作之後（§3.1）。
- **重新計時（不可節流）**：只要**登記**到一張新照片，5 秒無新照片的緩衝計時**一律立即重新起算**，這是「不漏收」的核心保證，不能因畫面更新頻率而打折扣。
- **畫面更新（採雙門檻節流）**：「⏳ 確認中…（目前共 X 張…）」的張數更新採「時間或張數，滿足其一即更新」的雙門檻（見 §6.3.1），並以**原地編輯**為主、定期才「刪舊發新」拉回底部，兼顧「數字看得到在跳」與「不觸發 Telegram 限流（429）」。

使用者主動點擊按鈕（首次點「我傳完了」、或緩衝期間重複點擊）時的「確認中」回覆，**永遠立即顯示、不受節流影響**——節流只套用在「照片自動觸發的畫面更新」，不套用在使用者的主動操作上。

> **v2 的教訓**：v2 讓「確認中」的節流沿用 `COUNTER_UPDATE_SEC`（5 秒），而結案緩衝也是 5 秒，兩個窗一樣長，且點按鈕時還把節流計時歸零——結果「確認中」的張數**幾乎不可能更新到哪怕一次**就被刪掉換成進度條。這正是使用者回報「數字不會跳」的直接原因。故 v3 明訂「確認中」使用**獨立且更靈敏**的節流參數，不得與收件階段共用。

**已知限制：手機端的「傳送中」與 bot 端的「已收到」是兩件事**

手機選取多張照片後，Telegram 用戶端會依序把每張排入自己的上傳佇列（畫面上看到的轉圈圈），這段上傳到 Telegram 伺服器的時間 bot 完全看不到、也無法查詢。若使用者在手機仍有照片轉圈圈上傳中時就按下「✅ 我傳完了」，而該張照片的伺服器端上傳耗時超過 5 秒緩衝，就可能被排除在這一批之外。**這是 Telegram 用戶端行為造成的限制，程式無法從伺服器端完全消除**，只能靠緩衝盡量降低機率。因此**操作建議**（顯示於教學或適時提醒）：**等對話視窗裡自己傳的那些照片都出現「兩個勾勾」之後，再按結束按鈕**。

> **為何用「兩個勾勾」而不是「不再轉圈圈」**：Telegram 的訊息狀態標記中，**一個勾勾**代表已送達伺服器、**兩個勾勾**代表對方（bot）已讀取。等到兩個勾勾出現，才是「這張照片確實已經到 bot 手上」的明確信號，比觀察縮圖是否還在轉圈圈更容易辨識、也更準確。此建議由實機測試的使用者提出。

**重複點擊的處理**

| 情境 | 行為 |
|---|---|
| 重複點「📷 我要上傳照片」 | 若已在 session 中，忽略後續點擊，並回覆目前狀態，不重置流程 |
| session 進行中收到 `/start` | 與重複點「📷 我要上傳照片」同義：顯示目前進度狀態，**不當作歡迎新使用者處理**、不重置流程（避免長輩誤觸 `/start` 以為進度被清空） |
| 尚未收到任何照片就點結束 | 回覆「尚未收到任何照片喔！請先在手機上選擇照片傳送給我，傳完再按此按鈕。」並**擋下**，不建立空資料夾、不結束 session（v3.1 新增防呆） |
| 重複點「✅ 我傳完了」 | 首次點擊後即進入緩衝並顯示「⏳ 確認中…已收到 X 張」；緩衝期間**再次點擊不縮短、不重啟緩衝計時、不重複計數**，但**仍會重新顯示同一則「確認中」訊息**（而非完全無回應），避免使用者誤以為沒點到而重複猛戳 |
| 重複點「↩️ 這批傳錯了」 | 首次點擊後即進入更正流程，該批按鈕失效，避免重複複製 |

**media group（相簿）聚合**

手機以「相簿」方式一次選取多張傳送時，Telegram 會拆成多個獨立 update 送達，各帶相同的 `media_group_id`。程式須依此 ID 聚合，避免計數重複、進度條跳動錯亂。

程式內部為了穩定性，會把這一次上傳再拆成數個「**內部小批**」（預設每 20 張）分次寫入——但**這對使用者完全透明**：所有回報與「這批傳錯了」的判定，一律以「**使用者的這一次上傳**」為單位，而非內部小批。

> **範例 1**：這次傳 100 張，程式內部拆成 5 批寫入 → 使用者點「這批傳錯了」，處理的是**全部 100 張**。
> **範例 2**：先傳 100 張並按「我傳完了」完成，接著再傳 20 張 → 對這 20 張點「這批傳錯了」，處理的是**這 20 張**，不含先前的 100 張。

**流程**

```
Bot:   ✅ 準備好了！資料夾：阿嬤生日 ／ 存到：家裡硬碟
       請開始傳照片，傳完後點下方按鈕
       [✅ 我傳完了]              ← 全程常駐

媽媽:  [開始傳照片…]
Bot:   📥 已收到 47 張（已存好 40 張）        ← 同一則訊息，刪舊發新永遠置底
       [⚡ 沒照片了，發送並寫入]

媽媽:  [等對話裡自己傳的照片都出現兩個勾勾（代表都送出去了），才點結束]
Bot:   📥 已收到 68 張（已存好 60 張）        ← 還是同一則訊息，只是多了下面這行
       ⏳ 確認中，稍等一下，我再看看還有沒有照片進來…

       📥 已收到 83 張（已存好 70 張）        ← 張數持續跳動（原地編輯）
       ⏳ 確認中，稍等一下，我再看看還有沒有照片進來…
       （緩衝秒數內都沒有新照片 → 正式結案）

Bot:   📤 上傳中 ▓▓▓▓▓▓▓▓░░ 80%（80/100 張）   ← 取代「確認中」，持續更新
       ✅ 完成！100 張 → 阿嬤生日（家裡硬碟）
       [↩️ 這批傳錯了]
```

1. **收到照片 update** → 事件處理層**立即登記**（記下 `file_id`、張數 +1）、視節流更新畫面、重設緩衝計時，然後**立刻返回**。實際下載交給下載 worker（§3.1）。
2. **下載 worker** 把照片落地到該次的暫存子夾（見 §4.3）。
3. **收件階段**（尚未點「我傳完了」）：複製 worker 每累積滿 20 張（內部小批）即複製到目的地，成功後刪除該批暫存檔。此階段的備份進度顯示在收件計數訊息的「（已存好 N 張）」（§6.3.1）。
4. 使用者按「✅ 我傳完了」→ **事件處理層立即回覆「⏳ 確認中…」**（毫秒級，不受下載佇列深度影響）→ 進入 5 秒確認緩衝。**緩衝期間收到的照片仍照常登記、計數、重設計時，但其複製動作遞延**，不在此階段啟動新的內部小批。
5. 緩衝結束 → **先等待所有尚未完成的下載工作全部落地**（§6.3 批次定義），再處理「收件階段剩下的尾巴」＋「緩衝期間收到、尚未複製」的全部照片，統計總數。
6. 以**進度條＋百分比＋張數**回報，完成後附「↩️ 這批傳錯了」。
7. **同一資料夾再次上傳**：完成後直接再傳即可，不需重設，並視為**新的一次上傳**。

> **設計取捨一（分批時機）**：收件階段（點「我傳完了」之前）仍維持每 20 張分批複製，這是為了避免大量照片（如 500 張）全部堆到最後才一次寫入網芳的風險（見 §12.2），同時也讓暫存區不會累積整批照片（見 §6.3.3）。但緩衝期間（點了「我傳完了」之後、確認收齊之前）刻意停止啟動新的小批，換來體驗上更明確的「確認中 → 上傳中」階段分野。
>
> **設計取捨二（進度條可能一出現就接近 100%）**：因為收件階段已在背景把大部分照片備份完成，緩衝結束時剩餘工作往往很少，進度條可能一出現就是 80%、90%，甚至已全部完成。**這是正確且誠實的呈現，不是缺陷**——照片確實早就存好了。故：
> - 收件階段的計數訊息必須同時顯示「（已存好 N 張）」，讓使用者一路看得到備份進度，進度條的起跳點才不突兀；
> - 若緩衝結束時所有照片皆已寫入完成，**直接顯示「✅ 完成」即可，不必為了畫面效果假造一段進度條**。

**忘記按按鈕的保險機制**
若使用者傳完照片後未按「✅ 我傳完了」，於 **session 逾時（10 分鐘無動作）**時，自動將已收到的照片視為一批處理完成，並通知使用者與管理員，避免照片滯留暫存區無人處理。

### 6.3.1 即時進度回饋（避免使用者誤判當機）

長輩若感覺「沒反應」極易重複上傳，故全程須有明確的運行訊號：

| 機制 | 做法 |
|---|---|
| **單一狀態訊息（v3.2 合併，重要）** | 收件階段與確認階段**共用同一則訊息**，全程只更新它一則。<br>v3.1 以前分成「📥 收到照片中… X 張」與「⏳ 確認中…（目前共 X 張）」**兩則**訊息，但兩者講的其實是同一件事——「還在收，目前 X 張」——只是使用者按過結束按鈕沒有的差別。為此刪一則、發一則，畫面雜訊大於資訊量，實測回饋即為「這兩個訊息在講一樣的事情」。<br>合併後**唯一的差異是句尾的狀態標記**：<br>‧ 收件中：`📥 已收到 47 張（已存好 40 張）`<br>‧ 按下結束後：同上，再加一行 `⏳ 確認中，稍等一下，我再看看還有沒有照片進來…`<br>這一行既是狀態說明，也是**「你按到了」的回饋**——沒有它，使用者按下按鈕後畫面不會有任何變化（數字本來就一直在跳），會重蹈「傳完了按下去沒動靜」的覆轍。 |
| **狀態訊息的更新方式（依階段不同）** | ‧ **收件階段：刪舊發新**。使用者正在傳照片，每張照片都會在對話中形成新訊息把狀態訊息往上推；唯有刪掉舊的、在**最下方**重發，才能讓它永遠緊貼在已傳照片的最下面，不需捲動即可看到。此為實測後依使用者明確指示保留的設計，取代最初規格「原地編輯不洗版」的字面做法。<br>‧ **確認階段：以原地編輯為主**。使用者已停手，改用 `editMessageText` 更新數字——單次 API 呼叫、不閃爍、數字直接跳；只有隔了 `COUNTER_REANCHOR_SEC` 秒才再刪舊發新把它拉回底部（緩衝期間仍可能有照片陸續抵達把它推上去）。<br>‧ **使用者主動點擊按鈕時：一律原地編輯，絕不刪除重發**。他剛點的按鈕就在這則訊息上，訊息本來就在眼前，不需要移動位置；刪掉重發反而會讓他看到訊息憑空消失（實測回饋：「我點選沒照片了，那個訊息就被刪除了！」）。原地編輯同時也是最即時的回饋——「⏳ 確認中」那一行會直接在原處長出來。<br>‧ 若原地編輯失敗且原因是「內容完全相同」（Telegram 的 `message is not modified`），代表本來就沒有東西要更新，**直接略過**，不可退回刪除重發。 |
| **雙門檻節流** | 節流條件為「距上次更新已達 N 秒」**或**「距上次更新已新增 M 張」，**滿足其一即更新**。收件階段用 `COUNTER_UPDATE_SEC`／`COUNTER_UPDATE_COUNT`，確認階段用 `CONFIRM_UPDATE_SEC`／`CONFIRM_UPDATE_COUNT`（更靈敏，因為此階段通常只剩尾巴幾張，要跳得明顯）。<br>⚠️ **不可只用時間門檻**：若一批照片在節流秒數內就全部抵達（張數不多、手機網路快時很常見），畫面會停在第 1 張的數字完全不動，直到使用者按結束才第一次看到正確總數，造成「感覺卡住、傳完了才有動靜」的錯覺——這是 v2 實測回報的問題之一。 |
| **狀態訊息同時顯示備份進度** | 顯示為 `📥 已收到 47 張（已存好 40 張）`。因為背景 worker 正同步進行複製，兩個數字並列可讓使用者一路看得到「收了幾張／已經安全落地幾張」，也讓緩衝結束後進度條的起跳點不突兀（見 §6.3 設計取捨二）。 |
| **上傳進度條** | 緩衝結束後，以 `▓▓▓▓░░░░` 進度條＋百分比＋張數呈現，分母為本次上傳的全部張數、分子為**已成功寫入所有目的地**的張數，每完成一個內部小批更新一次（此階段訊息原地編輯即可，因後續不會再有使用者傳的照片訊息插進來推擠版面）。進度條可能一出現就接近 100%，屬正常且誠實的呈現，處理方式見 §6.3 設計取捨二。 |
| **輸入中狀態** | 處理期間持續發送 Telegram「正在輸入…」／「正在傳送照片…」狀態，視覺上確認 bot 存活。 |
| **完成明確宣告** | 結束時明確顯示「✅ 完成！X 張 → 資料夾（目的地）」，讓使用者確知可以停手。若本次有照片與相簿既有的重複，加一句說明有幾張重複、已另存不會覆蓋（見 §10），避免使用者以為漏傳。 |
| **狀態訊息保留於對話紀錄** | 緩衝結束換上進度條時，**不刪除**狀態訊息（v3.0 原本會刪）。實測回饋是使用者想回頭對照「當時到底收到幾張」，留著比較安心；且此時已無新照片訊息插進來推擠版面，不構成洗版。 |
| **非授權操作的節流提醒** | 使用者在**未啟動 session** 時傳照片或打字（含當時仍在忙自己手機上傳、陸續傳來的殘留訊息），bot 提示「請先點『📷 我要上傳照片』開始喔」。此提醒**採 30 秒節流**（同一使用者 30 秒內只提醒一次），避免手機端因網路較慢、上傳佇列較長，在使用者已離開 session 後仍陸續送達殘留訊息時，被連續同樣的提醒訊息洗版。 |

### 6.3.2 寫入重試機制

因 SMB 網芳在連續大量寫入時可能出現暫時性錯誤（逾時、連線重置、裝置忙碌），設計三層防護：

| 層級 | 做法 | 可設定 |
|---|---|---|
| **下載重試（v3 新增）** | 從 Telegram **下載**照片失敗（網路瞬斷、API 逾時）時自動重試最多 `DOWNLOAD_RETRY_TIMES` 次。仍失敗則：① 於 `file_index.csv` 記一列，目的地欄標「下載失敗」、檔名欄留空，**保留 `file_id`** 供日後用 `redownload.py` 補救；② 通知管理員；③ 於本次結束時彙總告知使用者「有 N 張沒收到，麻煩再傳一次」。<br>⚠️ **絕不可靜默吞掉**——v2 的下載完全沒有例外保護，一旦失敗，該張照片不落地、不計數、不記錄，使用者與管理員都無從得知，直接違背 §2「照片不遺失」與 §16.1「成功或失敗一律記錄」。 | 次數 |
| **單檔重試** | 寫入失敗自動重試最多 3 次，間隔遞增（1s → 3s → 5s） | 次數、間隔 |
| **寫入節流** | 每張之間插入短暫延遲，避免高速連續寫入壓垮網芳 | 預設 0.3 秒 |
| **批次後重試** | 本次上傳結束後，自動將暫存區中仍失敗的檔案再重試一輪 | 開／關 |

三層皆失敗 → 檔案保留於暫存區（不刪），並通知管理員。

### 6.3.3 併發與資源上限（大量照片時的行為保證）

把下載與複製移到背景後，**必須明確規定並行上限**，否則「一次傳幾千張」會變成「同時開幾千個下載工作」，反而把磁碟、網路與網芳一起壓垮。本專案採**固定數量 worker ＋ 工作佇列**，並行度**不隨照片數量增加**。

| 資源 | 上限 | 理由 |
|---|---|---|
| 事件處理（update） | **1**（維持 python-telegram-bot 預設序列） | 事件處理已是毫秒級，序列不再是瓶頸；維持序列反而保證 session 狀態不會被並行改壞（見 §3.1） |
| 同時下載 | `DOWNLOAD_WORKERS`，預設 **3** | 兼顧下載速度與對 Telegram API 的禮貌。worker 數固定，傳 10 張與傳 3000 張的瞬時壓力相同 |
| 同時複製到目的地 | **固定 1** | 網芳（SMB）最怕並行寫入。維持現行「一批一批依序寫、每張間隔 `WRITE_THROTTLE_SEC`」的行為，完全不變 |
| 佇列內容 | 只有 metadata | 排隊中的項目只是 `file_id` 字串與時間戳（每張約數百 bytes），**不是照片本體** |

**一次傳 3000 張的資源估算**

| 項目 | 估算 | 說明 |
|---|---|---|
| 記憶體 | 約 **1～2 MB** | 3000 筆 metadata ＋ 各目的地的寫入路徑對照 |
| 暫存區磁碟 | 約 **20～100 MB**（**不是 3000 張的總和**） | 收件階段仍維持「每滿 20 張即複製到目的地並刪除該批暫存」，暫存區同一時間只留「尚未備份完」的數十張 |
| 磁碟／網路 I/O 總量 | **與 v2 完全相同** | 每張照片仍是「下載寫入暫存 1 次 ＋ 每個目的地複製 1 次 ＋ 刪暫存 1 次」。v3 只改變「由誰觸發、何時觸發」，**不改變工作總量** |

> **這是 v3 架構調整的關鍵保證**：沒有增加任何一次讀寫，只是把原本塞在事件處理函式裡的同一批工作搬到背景依序執行。使用者感受到的差別是「按鈕立刻有反應、張數會跳」，電腦感受到的負載與 v2 相同。

**真正的瓶頸仍在「目的地寫入」，不在「收件」**

會拖慢大批次的一直是網芳的寫入速度（每張 `WRITE_THROTTLE_SEC` 節流 ＋ 實際 SMB 複製時間），這一段 v3 完全沒有動。3000 張「🏠☁️ 兩邊都存」預期仍需數十分鐘才能全部複製完成——差別在於這段期間 bot 對所有按鈕與訊息**保持即時回應**，而不是整個卡住不動。

**暫存區空間的保護**

若目的地持續寫入失敗（例如網芳離線），失敗的檔案依「照片不遺失」原則會**保留在暫存區不刪**。大批次遇上長時間失敗時，暫存區可能累積到接近整批大小。此為刻意的取捨（寧可佔空間，也不遺失照片），但須：

- 管理員通知中明確標示「已保留 N 張於暫存區」，讓管理員知道要處理；
- `TEMP_DIR` 建議設在空間充足的磁碟（見 §4.3）。

### 6.3.4 靜置關懷提醒（v3.1 新增）

長輩傳照片時常會中途停下來（找相簿、被打斷、以為已經好了），若 bot 完全沉默，使用者不確定該不該按結束。故加入**主動關懷提醒**：

| 項目 | 規定 |
|---|---|
| 觸發條件 | 收件階段、**已收到至少 1 張**照片、且連續 `INACTIVITY_PROMPT_TIMEOUT_SEC`（預設 25 秒）沒有新照片 |
| 提醒內容 | `📥 看起來照片傳得差不多囉！目前共收到 X 張照片（已備份好 Y 張）。請問照片都傳完了嗎？` |
| 附帶按鈕 | `✅ 確定傳完了，開始上傳` ／ `📷 我還有照片沒傳完` ／ `🔄 重新開始` |
| **可重複觸發** | 收到新照片即重置提醒旗標，**下次再停頓一樣會提醒**，不是只提醒一次 |
| 點「我還有照片沒傳完」 | 回覆親切訊息並重置靜置計時，session 完全不受影響 |
| 訊息保留 | 提醒訊息**不會**因為收到新照片而被刪除收回，完整留在對話中供查閱 |

> **實際間隔說明**：逾時巡邏排程每 30 秒執行一次，故提醒的實際出現時間會落在 25～55 秒之間，而非精準的 25 秒。這對使用體驗無影響，但文件須據實記載。

### 6.4 工作階段逾時（重要）

**計時起點的定義**

10 分鐘計時**僅在「完全閒置」時累計**。以下狀態**不計入**閒置時間，session 不會逾時：

- 程式正在處理中（下載、複製、重試、進度回報中）
- 正在等待使用者操作（已顯示選項按鈕、等待選擇資料夾或目的地）
- 結案緩衝（Debounce）進行中

> 大量照片（如 500 張）處理可能耗時數分鐘，此定義可避免處理過程中誤觸逾時。**計時自「本次處理全部完成、且無待回應動作」的那一刻起算。**

- **完全閒置超過 10 分鐘**，該工作階段視為逾時：
  - 當前選擇的「資料夾／目的地」**設定值失效**。
  - ⚠️ **此處僅清除程式記憶體中的選擇狀態，不影響任何實體檔案**——目的地（區網硬碟／OneDrive）的照片完全不動，暫存區也不會因逾時而清空（暫存區的清理只發生在「該批複製成功後」，見 §4.3）。
  - 「近 3 次資料夾」的記憶**仍保留**（供下次快速選）。
- 逾時後，家人**必須重新點「📷 我要上傳照片」按鈕**才能再次上傳。
- 逾時後若直接打字或傳照片 → bot 提示「請先點『📷 我要上傳照片』開始喔」。
- **逾時同時觸發兩件事**：
  1. 若有尚未按「我傳完了」的照片，自動當作一批處理完成（見 §6.3 保險機制）。
  2. 對本 session 期間寫入 OneDrive 的檔案執行釋放空間 `attrib +U -P`（見 §4.2）。

**選資料夾／目的地階段的絕對存活上限（記憶體保護，非取代上述閒置豁免）**

§6.4 上述「處理中／等待使用者選擇」不計入閒置的規則維持不變——這是刻意設計，避免長輩選到一半被系統打斷。但若使用者點了「📷 我要上傳照片」後**從未實際傳過任何照片**就離開（如切出對話、忘記回來），該 session 會停在選擇階段永遠不觸發上述 10 分鐘閒置逾時，長期下來可能在記憶體中累積殘留。因此另加一道**獨立的絕對存活上限**（`ABANDONED_SESSION_MAX_MIN`，預設 60 分鐘）：僅當「**已收到的照片數為 0** 且 **session 建立時間超過此上限**」才靜默清除，**不通知使用者、不通知管理員**（因為使用者本來就什麼都沒傳，沒有照片風險）。此機制與「處理中／選擇中不算閒置」的原則並不衝突：只要收到過至少 1 張照片，就完全不受此上限約束，回歸原本的 10 分鐘閒置規則。

**所有「非收件」階段也須有兜底逾時（v3 新增）**

上述 10 分鐘閒置逾時只在「已選好資料夾、等待傳照片」的收件階段累計。但 session 也可能停在其他階段回不來——例如使用者按了「🔄 重新開始」卻始終不回答二次確認、或緩衝計時因程式異常未被觸發。這些狀態下 session **既不會逾時、也不符合「絕對存活上限」的條件**（因為已收到過照片），會永久佔用記憶體，且暫存區的照片無人收尾。

故除收件階段的 10 分鐘閒置外，**任何階段停留超過 `STAGE_STUCK_MAX_MIN`（預設 30 分鐘）一律視為異常**：比照逾時流程把已收到的照片當一批處理完成，並通知管理員。**不可靜默丟棄**——暫存區可能還有照片。

### 6.5 重新開始（中止本次上傳）

**按鈕配置**

兩顆按鈕語意分離，避免誤觸：

| 按鈕 | 出現時機 | 功能 |
|---|---|---|
| `📷 我要上傳照片` | **未在 session 中**時常駐 | 啟動新的上傳 session |
| `🔄 重新開始` | **session 進行中全程顯示**（選資料夾、選目的地、傳照片、處理中皆可見） | 中止本次上傳，一切從頭來 |

> 兩者不可混用：`📷 我要上傳照片` 在 session 中被點擊時僅回覆目前狀態、不重置（見 §6.3 重複點擊處理）；真正的重來一律走 `🔄 重新開始`。

**二次確認（必要）**

按下 `🔄 重新開始` 後**不立即執行**，先跳出確認：

```
Bot:   ⚠️ 確定要重新開始嗎？
       目前已收到的 47 張照片將不會繼續上傳，需要重新傳送。
       [✅ 確定重來]  [❌ 取消，繼續原本的]
```

**執行內容**

確認後執行：

1. **清空記憶體狀態**：當前選擇的資料夾、目的地、本次計數全部歸零。
2. **刪除本次的暫存子夾**：移除該使用者本次上傳的第二層暫存夾及其中所有檔案（位於 `TEMP_DIR` 內，符合刪除圍籬規範）。
3. **回到起點**：顯示 `📷 我要上傳照片`，使用者需重新選擇資料夾與目的地，照片需重新傳送。

**已寫入目的地的照片如何處理（重要）**

因採「每滿 20 張即複製到目的地」的分批機制，按下重新開始時**可能已有部分照片寫入區網硬碟／OneDrive**。處理原則：

| 位置 | 處理 |
|---|---|
| 暫存區（本次子夾） | **刪除**（符合刪除圍籬，暫存區為唯一可刪區域） |
| 區網硬碟／OneDrive **已寫入的照片** | **保留不動，程式絕不刪除** |

- 對**使用者**：不提及殘留檔案，僅回覆「已重新開始，請重新選擇資料夾」。
- 對**管理員**通知：`⚠️ 使用者中途重新開始，「阿嬤生日」已寫入 40 張為中止殘留，詳見待清理清單`。
- **寫入 `data/待清理清單.csv`**：逐筆記錄已寫入目的地的檔名、所在資料夾、上傳者、時間（見 §10B），供管理員精準刪除。
- 使用者重傳後，因檔名時間戳不同，舊檔不會被覆蓋，將形成重複檔案，由管理員依待清理清單手動清理。

> **為何不一併刪除目的地檔案**：零刪除是本專案最核心的安全保證。若為支援「乾淨重來」而讓程式具備刪除目的地檔案的能力，該防線即告破除——日後任何程式錯誤都可能誤刪照片。中止殘留由人工清理是可控的；讓程式能刪照片則不可控。

### 6.6 遲到照片自動併案（v3.1 新增）

**情境**：使用者按了「結束」、bot 也回報完成之後，手機仍在背景陸續送出最後幾張，或使用者突然想起漏了幾張又補傳。此時 session 已經結束，照 §6.1 規則 bot 只會回「請先點『📷 我要上傳照片』開始喔」，使用者得重新選一次資料夾與目的地——對長輩而言相當挫折。

**規則**

| 項目 | 規定 |
|---|---|
| 觸發條件 | 目前**沒有進行中的 session**、且上一批完成時間在 `AUTO_APPEND_WINDOW_MIN`（預設 3 分鐘）內、且該批**尚未被「這批傳錯了」更正過** |
| 動作 | 自動開一個指向**上一批相同資料夾與目的地**的 session，照片直接歸案 |
| 使用者訊息 | `💡 收到補傳的照片，會自動幫你存進剛剛的「X」相簿` |
| 結束方式 | 直接進入結案緩衝（`STAGE_DEBOUNCE`），收齊後自動結案，**使用者不必再按一次結束** |

**實作硬性要求：必須重用正常流程，不得另闢路徑**

自動併案**必須**透過「開一個正常的 session」來完成，讓照片走與一般上傳完全相同的管線。**嚴禁**為它另外寫一條「直接下載並複製」的捷徑——那樣會重蹈 v2 的覆轍：

- 在事件處理函式裡同步下載，會堵住 update 佇列（違反 §3.1）；
- 另一條路徑必然漏掉下載重試、失敗通知、`file_index.csv`、`upload_log.csv`、`written_paths`（「這批傳錯了」要用）等既有保護；
- 上傳者欄位若改用 Telegram 暱稱而非註冊稱呼，會與其他紀錄不一致（見 §10B 欄位對應要求）。

重用正常流程可讓上述保護**全部自動繼承**，不需要把同一套容易出錯的邏輯再實作一遍。

## 7. 傳錯復原機制

當家人點 `↩️ 這批傳錯了`：

1. bot 詢問這批照片要改放到哪個資料夾——**須同時提供「近 3 次資料夾」按鈕與打字輸入兩種方式**（介面比照 §6.2 的選資料夾），不可只接受打字。
2. bot 把這批照片**複製**到正確的新資料夾。
3. **原本傳錯位置的照片保留不動**（機器人不刪）。
4. 對**家人**只回覆：`✅ 已經幫你把這 X 張改放到「新資料夾」了`（不提背後處理）。
5. 對**管理員**通知：`從「A 資料夾」改放到「B 資料夾」，A 裡有 N 張需要你手動清理，詳見待清理清單`（通知本身不列檔名）。
6. **寫入 `data/待清理清單.csv`**：逐筆記錄**原位置（錯誤資料夾）**中需刪除的檔名、路徑、上傳者、時間（見 §10B）。新位置為正確結果，不記錄於待清理清單。
7. **寫入 `data/file_index.csv`**：新位置（正確資料夾）的每一張照片，比照正常上傳流程**逐張記錄新的一列**（含原本的 file_id、新目的地、新檔名）。**這是必要的**——`file_index.csv` 是「這個目的地實際有哪些照片、對應哪個 file_id」的完整索引（見 §10D、§16），若更正後的新位置不記錄，該工具日後就無法用 `redownload.py` 找回這批照片，索引會出現缺口。
8. **`data/upload_log.csv` 也記一筆**：資料夾欄位寫成 `A資料夾 → B資料夾`、結果欄位為「傳錯更正」（見 §10A 範例列），與正常上傳共用同一份歷史紀錄表，方便日後查詢「這個資料夾是怎麼形成的」。
9. 若原批次為「🏠☁️ 兩邊都存」，**張數以實際照片數計算**（同一張照片在兩個目的地各成功複製一次仍算 1 張），不因目的地數量而加倍——使用者訊息、管理員通知、`upload_log.csv` 三處張數需一致。
10. **「等待輸入新資料夾」的狀態必須有明確失效條件（v3 新增）**：使用者點了「↩️ 這批傳錯了」卻不回覆（改變主意、關掉對話）時，此待輸入狀態不可無限期存在。否則使用者下一次開新的上傳、輸入資料夾名稱時，那個名稱會被誤判成「更正目標」——結果是**上一批照片被複製到新上傳的資料夾去，而新的 session 還卡在等資料夾名稱**。失效條件有兩個，滿足其一即清除：<br>① 使用者**開始新的上傳 session** 時立即清除；<br>② 超過 `CORRECTION_PROMPT_MAX_MIN`（預設 10 分鐘）自動失效。<br>另：若使用者輸入的資料夾名稱經過濾後為空字串，須明確回覆請他重新輸入，**不可靜默無反應**。

> **「這批」的定義**：指「使用者最近一次上傳」的全部照片（見 §6.3 批次定義），而非程式內部拆分的小批。程式會記住該次上傳每張照片的 file_id 與各目的地實際寫入路徑（寫入當下即配對，不依賴事後用順序反推），復原時據此全數再複製。

## 8. 錯誤與失敗處理

| 情境 | 對家人 | 對管理員 | 照片處理 |
|---|---|---|---|
| **傳錯資料夾** | 「✅ 已經幫你把這 X 張改放到「新資料夾」了」（**完全比照 §7 傳錯復原機制**） | 「從 A 改到 B，A 裡有 N 張需要你手動清理」（不列檔名） | 複製到新夾，原檔保留不刪 |
| **寫入失敗**（網芳暫時性錯誤、磁碟滿、權限、檔案被佔用等） | 「出了點狀況，已通知管理員」 | 寫入失敗 + 錯誤原因 + 已保留於暫存區 | 先經三層重試（§6.3.2）；仍失敗則保留暫存區不刪 |
| **同名檔案** | 無感（正常回報） | 記 log | 自動改名另存（加時間戳／流水號），**絕不覆蓋** |
| **未設資料夾就要傳** | 「請先選資料夾」 | — | — |
| **傳送非圖片檔案**（影片、動圖、語音、貼圖、非圖片文件等） | session 進行中收到時，回覆「目前僅支援照片，這個檔案類型還沒辦法處理」，不下載、不計入張數 | — | 完全不處理、不落地暫存區 |
| **未登記帳號來訊** | 顯示歡迎訊息 ＋ `📝 我要註冊` 按鈕（首次開啟對話時由 START 觸發，bot 主動發送） | 「有新登記：名字 + ID」＋開通／拒絕按鈕 | — |
| **已登記未開通者來訊** | 「已收到登記，等管理員開通後就能使用」 | 「未開通者來訊（名字 + ID）」 | — |
| **記錄檔被鎖住無法寫入**（管理員用 Excel 開著 CSV） | 無感，照片與回覆完全正常 | 🔴 說明是哪個檔案、最可能是 Excel 鎖檔、請關閉後即恢復；並註明照片不受影響、漏掉的內容可到 `logs/photo-bot.log` 查回 | 照片照常處理；未寫入的紀錄留在程式 log |
| **連線健檢失敗**（啟動時／開 session 時） | 「現在暫時無法上傳，請稍後再試」 | 🔴 健檢失敗 + 錯誤原因 | 事前攔阻，不收下照片 |
| **「兩邊都存」部分失敗** | 「有一部分還在處理中，已通知管理員」 | 分別列出兩邊狀態（成功／失敗＋原因） | 暫存不刪，只重試失敗那一邊 |
| **使用者中途重新開始** | 「已重新開始，請重新選擇資料夾」 | 「中途重新開始，某資料夾有 N 張中止殘留，請確認是否清理」 | 暫存區本次子夾刪除；目的地已寫入者保留不動 |
| **程式中斷後重啟** | （若涉及其上傳）告知復原結果 | 復原報告：哪些批次、幾張、成功或失敗 | 自動補送；失敗則保留暫存不刪 |
| **從 Telegram 下載照片失敗** | 於本次結束時彙總告知「有 N 張沒有收到，麻煩再傳一次」（不逐張打擾） | 下載失敗張數 ＋ 錯誤原因 | 先經下載重試（§6.3.2）；仍失敗則記入 `file_index.csv`（目的地欄標「下載失敗」，保留 `file_id` 供 `redownload.py` 補救），不落地暫存區 |
| **按鈕點擊逾時失效**（Telegram callback query 過期） | 不顯示技術錯誤；按鈕仍可再按一次即生效 | 記 log | 對 `answerCallbackQuery` 的失敗**必須包例外處理並繼續執行後續動作**，不可讓整個點擊處理中斷（v2 曾因此在大批次時「✅ 我傳完了」完全失效） |
| **未被個別處理函式攔下的例外** | 「出了點狀況，已通知管理員」 | 🔴 例外類型 ＋ 發生位置 ＋ 堆疊摘要 | 由全域 error handler 統一接住（見 §17），不可讓例外靜默消失 |

**共同原則**：照片不遺失、目的地的照片機器人不刪除、一律通知管理員。

## 9. 管理員通知清單

以下事件一律以 Telegram 私訊發給**固定的管理員帳號**（與家人的對話分開）：

- ✅ 每次成功上傳（上傳者、資料夾、張數、目的地）
- ⚠️ 傳錯更正（從哪改到哪、原位置剩幾張要清）
- 🔄 使用者中途重新開始（哪個資料夾有幾張中止殘留待清理）
- 🔴 寫入失敗（原因 + 重試結果 + 已保留於暫存區）
- 🆕 新成員註冊（名字 + ID，附開通／拒絕按鈕）
- 🔔 已登記未開通者來訊（名字 + ID）

> 所有通知一律只給「**資料夾 + 張數**」，不列出檔名。

## 10. 檔案命名規則

**時間來源優先序（重要）**

檔名的時間戳**優先採用照片的 EXIF 拍攝時間**（`DateTimeOriginal`），讀取不到才回退為接收時間。

| 順序 | 來源 | 說明 |
|---|---|---|
| 1 | EXIF `DateTimeOriginal` | 照片實際拍攝時間 |
| 2 | 接收時間（fallback） | EXIF 缺失、損毀或格式不支援時使用 |

> **為何如此設計**：家人上傳的很可能是舊照片（翻拍、舊手機整理後補傳）。若一律以接收時間命名，2008 年的照片會被標成 2026 年，破壞相簿時間軸的真實性——這與既有硬碟中「時間＋事件」的命名慣例相衝突。
> 實作使用 Pillow 或 exifread 讀取，屬輕量依賴，不違反「不使用 LLM」的確定性原則。

**命名格式（v3.1 改為永久指紋）**
- 格式：`YYYYMMDD_HHMMSS_{指紋}.jpg`，例如 `20080227_143015_a1b2c3d4.jpg`。
- **指紋來源：照片內容的 MD5 前 8 碼**。照片落地暫存區時算一次並快取，「📦 兩邊都存」時兩個目的地共用同一個值，不重複計算。
- ⚠️ **絕不可拿 `file_id` 當指紋**：Telegram 明訂 `file_id` 會隨 bot 與時間變動，同一張照片重傳會得到不同的 `file_id`，用它當「永久指紋」自我矛盾。
- ⚠️ **絕不可截取 `file_unique_id` 的子字串**（v3.5 實測踩到的坑）：`file_unique_id` 是 base64 編碼的結構，**變動的部分在前面**，後面是固定的類型／資料中心標記。原本取後 8 碼，結果實測 24 張照片有 **23 張**都算出同一個指紋 `aaifkivc`，同一秒收到的照片於是全部撞名，一路 `_(2)`、`_(3)`、`_(4)` 疊上去。若真要用它，**必須整串做雜湊**，不可截取任一段。
- **為何內容雜湊是更好的選擇**：同一張照片就算使用者重新從相簿傳一次（Telegram 會發給它不同的 `file_unique_id`），只要內容相同就會得到相同的指紋，「重複上傳」在檔名層次依然看得出來。指紋也因此完全不依賴 Telegram 未公開的識別碼格式。
- **這樣設計的效益**：同一張照片無論何時傳送，產生的檔名都完全相同，因此「重複上傳」在檔名層次就看得出來（見下方撞名處理），不需要額外比對。
- 舊格式為 `YYYYMMDD_HHMMSS_微秒.jpg`（微秒取自接收時間），同一張照片重傳會得到不同檔名，無法辨識重複。

**撞名處理：自動改名另存，絕不覆蓋（硬性規定）**

撞名（指紋檔名完全相同）代表**這張照片相簿裡已經有了**。此時：

| 動作 | 規定 |
|---|---|
| 既有檔案 | **完全不動**。自動改名另存為 `_(2)`、`_(3)`… |
| 待清理清單 | 新存的那份**逐筆寫入 `data/待清理清單.csv`**，類型為「重複檔案」（見 §10B） |
| 使用者訊息 | 完成宣告加一句「其中 N 張跟相簿裡已經有的照片是同一張，已另外存一份（不會覆蓋原本的）」 |
| 管理員通知 | 另發一則，說明有幾張重複、已記入待清理清單 |

> **為何不「直接覆蓋」**（v3.1 明確否決的提案）
>
> 曾有「既然指紋檔名相同就是同一張照片，直接覆蓋即可，才不會產生無意義的 `_(2)`」的提案。經評估後**否決**，理由：
> 1. **覆蓋是破壞性寫入**。`shutil.copy2` 對已存在的目的地會先把它清空（`open(dst,'wb')`）。若寫到一半網芳斷線——本專案實際遇過（§4.1 WinError 50）——原本那張好照片沒了，新的那張又不完整，**兩張都救不回來**。改名另存最壞情況只是多一個檔案。
> 2. **它推翻了 §11.3 的整個安全論證**。本專案的防刪除保證明白寫著「bot 雖然（透過讀寫帳號）具備刪除的權限，但程式碼『選擇』永不執行刪除。這道防線已足夠，因為程式公開可審」。一旦程式碼裡存在破壞性寫入，這條論證就不成立了。
> 3. **收益與風險不對稱**。覆蓋能省下的只是「幾個重複檔案」，代價卻是「照片可能永久損毀」。重複檔案由管理員照待清理清單刪除是可控的；覆蓋出錯則不可逆。
>
> 「使用者傳了 15 張、其實只有 6 張不同」的困惑，改由**完成訊息明講重複張數**＋**待清理清單列出可刪檔名**解決，不需要動用覆蓋。
- **不在檔名或資料夾名中加入上傳者資訊**，以維持既有相簿的命名慣例（時間＋事件）整潔。上傳者由上傳紀錄表追蹤（見 §10A）。

## 10B. 待清理清單（管理員手動刪除依據）

因程式對目的地採**零刪除**原則，某些情境會在區網硬碟／OneDrive 留下需人工清理的檔案。為使管理員有明確依據，所有此類檔案一律記錄於**單一檔案** `data/待清理清單.csv`。

**格式**

| 時間 | 上傳者 | Telegram ID | 類型 | 待刪位置 | 檔名 | 備註 |
|---|---|---|---|---|---|---|
| 2026-07-23 21:40 | 秀琴 | 123456789 | 中止殘留 | `\\192.168.1.1\g\照片\阿嬤生日` | 20080227_143015_123456.jpg | 使用者重新開始，已寫入 40 張中的第 1 張 |
| 2026-07-23 22:15 | 秀琴 | 123456789 | 傳錯更正 | `\\192.168.1.1\g\照片\阿嬤生日` | 20080227_143022_654321.jpg | 已改放至「阿公生日」，此為原位置殘留 |

> **欄位務必對應**：`上傳者` 欄一律填**上傳者的姓名**，不可填入目的地標籤或其他值。三種來源（中止殘留、傳錯更正、重複檔案）共用同一份 CSV，任一處欄位錯位，管理員就無法依人篩選或排序。

**記錄的三種來源**

| 類型 | 產生時機 | 記錄內容 |
|---|---|---|
| **中止殘留** | 使用者按「🔄 重新開始」，但部分照片已寫入目的地（§6.5） | 已寫入目的地的每一個檔名、所在資料夾、上傳者 |
| **傳錯更正** | 使用者按「↩️ 這批傳錯了」，照片已複製到新資料夾（§7） | **原位置**（錯誤資料夾）的每一個檔名——此為需刪除者；新位置為正確結果，不記錄 |
| **重複檔案** | 使用者重複上傳同一張照片（指紋檔名相同，見 §10），或重新開始後重傳形成新舊並存 | **新存的那份副本**（`_(2)` 等）逐筆記錄。既有的原檔是正確結果，不記錄——要刪的是多出來的副本 |

**使用方式**
- CSV 格式可直接以 Excel 開啟，支援排序與篩選（例如依資料夾分組，一次清理同一夾）。
- **程式只會新增，不會自行清空或刪除此檔內容**——清理與清單維護皆為管理員的手動動作。
- 若同時選擇「🏠☁️ 兩邊都存」，兩個目的地的殘留分別記錄兩列。
- 檔案位置：`data/待清理清單.csv`（列入 .gitignore，不進版控）。

## 10C. 併發寫入控制（資料檔安全）

`members.json`、`upload_log.csv` 與 `待清理清單.csv` 可能被多人操作、背景重試執行緒同時寫入，若無保護可能造成檔案損毀。採**雙重機制**，皆為 Python 標準庫，不增加外部依賴：

| 機制 | 解決的問題 | 做法 |
|---|---|---|
| **單一寫入佇列** | 併發衝突 | 所有寫入需求送入 `queue`，由**單一背景執行緒**依序執行，天然序列化，不會有兩個寫入同時進行 |
| **原子寫入** | 寫到一半中斷 | 先寫入暫存檔，完成後以 `os.replace()` 原子性地取代目標檔。中途斷電時原檔完好無損 |
| **CSV 真 append 寫入** | 效能隨紀錄增多而劣化 | `upload_log.csv`／`file_index.csv`／`待清理清單.csv` 新增紀錄時採真正的檔案 append（`"ab"` 寫入模式＋`fsync`），而非「整檔讀進記憶體、串接、整檔覆寫」。避免累積數萬列後，每傳一張照片都要重讀重寫整份檔案 |

> 未採用 filelock 等外部套件，因單機小型專案以標準庫即可完整解決，減少依賴。

本專案產生三類記錄檔，**彼此獨立、各自成檔**，切勿合併：

## 11. 防刪除策略（實際環境定案）

「機器人絕不刪除照片」這個核心保證，經實地測試後確認**完全靠程式層實現**。以下說明為何，以及三道防線的實際狀態。

### 11.1 環境實測結論

| 項目 | 實測結果 |
|---|---|
| 硬碟型態 | 插在 **TP-Link 路由器**上的 USB 硬碟，透過 SMB 網芳分享 |
| 存取路徑 | `\\192.168.1.1\g\照片`（UNC） |
| 連線帳號 | `hn14332019`（讀寫），憑證已由 Windows 記住（`cmdkey` 確認） |
| 中文資料夾寫入 | ✅ 實測成功（PowerShell 建立「測試資料夾_請忽略」+ 寫檔通過） |
| 免帳密寫入 | ✅ 靠 Windows 已記住的憑證，自動帶入 |

### 11.2 三道防線的實際狀態

| 防線 | 狀態 | 說明 |
|---|---|---|
| **程式層零刪除** | ✅ **主力，一定有** | `storage.py` 完全不含 delete/move 指令，只用 `shutil.copy2` + `mkdir`。程式碼公開於 GitHub、可逐行審查。 |
| NTFS 拒絕刪除鎖 | ❌ 不適用 | 硬碟在路由器後面，Windows 看不到底層格式，也無法對它套 NTFS ACL。 |
| 路由器後台細緻權限 | ❌ 做不到 | TP-Link「安全共享」只能設整個分享的「讀寫 / 唯讀」（帳號 `hn14332019` 讀寫、`visit` 唯讀），**沒有「能寫但不能刪」的中間選項**。bot 必須寫入，只能用讀寫帳號，該帳號同時也能刪。 |

### 11.3 結論與風險說明

- **核心保證靠程式層**：bot 雖然（透過讀寫帳號）具備刪除的「權限」，但程式碼「選擇」永不執行刪除。這道防線已足夠，因為程式公開可審、且你會逐行確認 `storage.py`。
- **殘餘風險**：bot 執行期間，這台電腦對整個網芳擁有讀寫（含刪除）權限，故「別的程式」或「手滑」仍可能刪到照片，路由器擋不住。此風險與 bot 無關，屬一般檔案管理風險，建議另行定期備份重要照片。
- **OneDrive 端**：靠程式層零刪除保護即可，不另設鎖以免干擾同步。

## 11A. 區網硬碟連線與帳密設定

因連線帳號 `hn14332019` 的憑證已被 Windows 記住，採「**做法 A：靠 Windows 憑證，config 不放帳密**」，並在 config 預留帳密欄位以備切換。

| 做法 | config 帳密欄位 | 連線方式 | 適用 |
|---|---|---|---|
| **A（採用）** | 留空 | bot 用 UNC 路徑，Windows 自動帶入已記住的憑證 | 目前狀態，最省事、GitHub 零帳密 |
| B（備援） | 填 `hn14332019` + 密碼 | bot 自行帶帳密連線 | 憑證日後被清除、或換電腦時切換 |

**`storage.py` 邏輯**：config 帳密欄位為空 → 直接用 UNC 路徑（做法 A）；有填 → 用該帳密建立連線（做法 B）。切換不需改程式，只改 config。

> ⚠️ 做法 A 依賴 Windows「記住」`192.168.1.1` 的憑證。若日後重灌、手動清除 `cmdkey`、或 Windows 更新偶發清除，bot 會連不上——屆時重新以檔案總管連一次網芳並勾選「記住認證」，或改用做法 B 即可。

### 12.1 config.py 可調參數

```python
# ── 路徑設定（日後可自由調整）──────────────────

# ── 連線帳密（做法 A 留空，靠 Windows 憑證）──────

NAS_PASSWORD   = ""

# ── 行為參數 ────────────────────────────────
BATCH_SIZE            = 20    # 內部小批張數（見下方選值說明）
SESSION_TIMEOUT_MIN   = 10    # session 逾時（分鐘）；亦為「忘記按我傳完了」的保險
ABANDONED_SESSION_MAX_MIN = 60  # 選資料夾/目的地卻始終沒傳照片的 session，絕對存活上限（分鐘），見 §6.4
STAGE_STUCK_MAX_MIN   = 30    # 任何階段卡住不動的兜底逾時（分鐘），見 §6.4
RETRY_TIMES           = 3     # 單檔寫入重試次數
RETRY_DELAYS          = [1, 3, 5]   # 重試間隔（秒）
WRITE_THROTTLE_SEC    = 0.3   # 每張寫入間隔
RETRY_AFTER_BATCH     = True  # 本次結束後自動重試失敗檔
ONEDRIVE_FREE_SPACE   = True  # session 結束後釋放 OneDrive 本機空間
RECENT_FOLDERS_COUNT  = 3     # 記憶最近幾個資料夾
FINISH_DEBOUNCE_SEC   = 5     # 按「我傳完了」後的結案緩衝秒數

# ── 背景 worker（v3，見 §3.1、§6.3.3）──────────────
DOWNLOAD_WORKERS      = 3     # 同時下載照片的背景 worker 數；固定值，不隨照片數增加
DOWNLOAD_RETRY_TIMES  = 3     # 從 Telegram 下載單張照片的重試次數

# ── 畫面更新節流（v3 改為雙門檻，見 §6.3.1）─────────
COUNTER_UPDATE_SEC    = 5     # 收件計數：時間門檻（秒）
COUNTER_UPDATE_COUNT  = 8     # 收件計數：張數門檻（新增滿幾張就更新一次）
CONFIRM_UPDATE_SEC    = 2     # 「確認中」張數：時間門檻（秒），比收件階段靈敏
CONFIRM_UPDATE_COUNT  = 3     # 「確認中」張數：張數門檻
COUNTER_REANCHOR_SEC  = 5     # 「確認中」多久才用一次「刪舊發新」拉回對話底部

# ── 其他 ────────────────────────────────────
CORRECTION_PROMPT_MAX_MIN = 10  # 「這批傳錯了」等待輸入新資料夾的有效時間（分鐘），見 §7
INACTIVITY_PROMPT_TIMEOUT_SEC = 25  # 靜置多久主動關懷提醒（秒），見 §6.3.4
AUTO_APPEND_WINDOW_MIN = 3      # 遲到照片自動併案的時間窗（分鐘），見 §6.6
HEALTH_CHECK_ON_START = True  # 啟動時執行 SMB 健檢
HEALTH_CHECK_ON_SESSION = True  # 每次開 session 執行 SMB 健檢
RECOVER_ON_START      = True  # 啟動時掃描暫存區並復原未完成批次
USE_EXIF_TIME         = True  # 檔名優先採用 EXIF 拍攝時間
```

**節流參數的選值原則（v3）**

「確認中」階段的門檻**必須明顯比結案緩衝（`FINISH_DEBOUNCE_SEC`）短**，否則張數根本來不及更新就結案了——v2 兩者都是 5 秒，正是「數字不會跳」的成因。建議維持 `CONFIRM_UPDATE_SEC < FINISH_DEBOUNCE_SEC` 的關係。

### 12.2 批次大小（BATCH_SIZE）選值說明

預設 **20 張**，為穩定性與回饋頻率的平衡點：

| 批次大小 | 優點 | 缺點 |
|---|---|---|
| 5–10 張 | 單批失敗影響範圍小 | 對網芳的 I/O 開關次數多，反而增加暫時性錯誤機會；進度訊息更新過於頻繁 |
| **20 張（預設）** | 一批約 6–10 秒（含 0.3 秒節流），對網芳負擔溫和；100 張約更新 5 次進度，回饋頻率適中；失敗重試成本可接受 | — |
| 50 張以上 | 寫入效率高 | 單批失敗需重來的量大；網芳長時間連續寫入更易觸發逾時 |

> 考量既有經驗「大量複製到網芳時可能突發失敗」，批次不宜過大（失敗成本高）亦不宜過小（連線開關頻繁）。此值可於實測後自行調整。

## 13. 版本控管與機密管理（GitHub）

本專案將以 **public repository** 上傳 GitHub。因程式碼公開，**機密資訊絕對不可進入版本庫**——一旦 commit，即使事後刪除，git 歷史仍永久保留，且 public repo 會被自動掃描機器人在數分鐘內抓取盜用。

### 13.1 絕不可上傳的四類資訊

| 類別 | 範例 | 風險 |
|---|---|---|
| Telegram Bot Token | `123456:ABC-DEF...` | 等於 bot 密碼，外洩即被盜用 |
| Telegram ID | 管理員 ID、家人 ID | 隱私外洩 |
| 成員清單 | `data/members.json` | 家人姓名與 ID |
| 實體路徑 | `\\192.168.x.x\...`、`C:\Users\你的名字\...` | 洩漏內網結構與使用者名稱 |

### 13.2 設定與程式碼分離（甲案）

採用 `config.py` + `config.example.py` 雙檔設計：

| 檔案 | 內容 | 進 Git? |
|---|---|---|
| `config.example.py` | 設定範本，全部填假值／佔位符 | ✅ 進 |
| `config.py` | 你的真實設定（真 token、真路徑、真 ID） | ❌ 由 .gitignore 忽略 |
| `data/members.json` | 家人清單 | ❌ 忽略 |
| `.gitignore` | 告訴 git 哪些不要追蹤 | ✅ 進 |

**使用流程**：clone repo 後，把 `config.example.py` 複製成 `config.py`，填入真實值即可執行。`config.py` 因列在 `.gitignore` 中，git 完全不會追蹤，杜絕誤 commit。

### 13.3 `.gitignore` 內容（必備）

```gitignore
# 機密設定（真實值）
config.py
.env

# 家人清單與執行期資料
data/
pending/

# Log
*.log
logs/

# Python
__pycache__/
*.pyc
.venv/
venv/

# 作業系統
Thumbs.db
.DS_Store
```

### 13.4 Repo 必備檔案

| 檔案 | 用途 |
|---|---|
| `README.md` | 中文專案說明：功能、安裝、設定、執行步驟 |
| `requirements.txt` | Python 套件清單（如 `python-telegram-bot`），一行指令安裝 |
| `LICENSE` | 授權條款（建議 MIT，最寬鬆常見） |
| `.gitignore` | 機密隔離（見 §13.3） |
| `config.example.py` | 設定範本 |

### 13.5 Token 外洩應急步驟

若不慎將 token commit 上 public repo：

1. **立即作廢舊 token**：到 Telegram @BotFather → `/revoke` → 選該 bot → 產生新 token。**光刪 commit 沒用**，因為外洩的瞬間就可能已被抓取，唯一有效做法是讓舊 token 失效。
2. 把新 token 填入本機 `config.py`（不要 commit）。
3. （可選）若要清除 git 歷史中的痕跡，可用 `git filter-repo` 或 BFG Repo-Cleaner 重寫歷史，但**作廢 token 才是關鍵**，歷史清理是次要。

> 原則：**token 外洩，先作廢重生，再談其他。**

## 16. 照片重新下載工具（redownload.py）

當本機檔案出現落差（誤刪、複製不完整、硬碟異常），可用此工具從 Telegram 重新取回照片。

### 16.1 技術前提：必須事先保存 file_id

**Telegram bot 無法回溯讀取歷史訊息。** 照片一旦不是「當下正在接收」，bot 即無法取得——除非收到當時就記下該檔案的 `file_id`。

因此主程式須在收到每張照片時，**逐張**將 `file_id` 寫入 `data/file_index.csv`：

| 時間 | 上傳者 | Telegram ID | 目標資料夾 | 目的地 | 檔名 | file_id |
|---|---|---|---|---|---|---|
| 2026-07-23 21:40 | 秀琴 | 123456789 | 阿嬤生日 | 家裡硬碟 | 20080227_143015_123456.jpg | AgACAgUAAx... |

- **一張照片對應一個 file_id**，一對一，不合併。傳 100 張即產生 100 列。
- **成功或失敗一律記錄**，涵蓋範圍最廣。
- 附帶效益：此檔即為最完整的「應有照片清單」，可用於與實際硬碟內容比對。

> ⚠️ **file_id 有效期**：Telegram 未保證 file_id 永久有效，一般可維持數月至數年，但過舊者可能失效。此特性正好提供判斷依據——工具會明確列出哪些已無法下載，即為需請上傳者重傳的部分。

### 16.2 工具行為

**形式**：單一 Python 檔 `redownload.py`，雙擊或以 `python redownload.py` 執行，互動式問答，執行完即結束。**不做多指令 CLI**。

```
========================================
  照片重新下載工具
========================================
1. 阿嬤生日      (秀琴, 2026-07-23, 100 張)
2. 過年聚餐      (秀琴, 2026-07-23,  20 張)
3. 烤肉          (大姊, 2026-07-22,  45 張)

請輸入編號（可多選，用逗號分隔），或輸入 all 全部下載：
> 1

下載到哪裡？（直接按 Enter 用預設 D:\重新下載）
> [Enter]

下載中… ▓▓▓▓▓▓░░░░ 60% (60/100)

完成！
  ✅ 成功 97 張 → D:\重新下載\阿嬤生日\
  ❌ 失敗  3 張（file_id 已失效，需請上傳者重傳）
     20080227_143015_123456.jpg
     20080227_143022_654321.jpg
     20080227_143108_789012.jpg
     詳見 D:\重新下載\阿嬤生日\失敗清單.txt
```

**流程**
1. 讀取 `data/file_index.csv`，依「目標資料夾＋上傳者＋日期」分組列出。
2. 使用者輸入編號選擇（可多選或 all）。
3. 詢問下載位置，預設 `REDOWNLOAD_DIR`（config 設定，預設 `D:\重新下載`）。
4. 依 file_id 逐張向 Telegram 請求下載，顯示進度。
5. 完成後分別列出成功數與**失敗清單（逐一列出檔名）**，並另存 `失敗清單.txt`。

**設計約束**
- **僅下載，不自動寫入區網硬碟或 OneDrive**。下載後由管理員自行於檔案總管搬移，避免工具意外覆寫既有相簿。
- 沿用主程式的檔名規則（EXIF 優先），確保與原檔一致。
- 不具備任何刪除能力。

|---|---|
